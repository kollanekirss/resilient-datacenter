# Scheduled backups and overdue status

Continue the approved full product scope with explicit opt-in hourly or daily backups. Installing a timer is authorization for the documented brief service pause at those times, not for upgrades, pruning or unrequested external notifications. Require an existing successful repository snapshot before enabling a schedule. Preserve independent recovery-access acknowledgement from repository initialization.

The timer must execute a root-managed copy of a fixed backup runtime, never mutable files in the operator's checkout or home directory. Use Ubuntu's Python and its maintained PyYAML/cryptography packages for this small runtime, with pinned Restic retained. Record file hashes and refuse modification or adoption of unknown existing files. Timer enable/disable/status are distinct; disabling the timer must not terminate an in-progress consistent backup. Serialize schedule changes against backup/recovery operations. Hourly or daily UTC calendars use bounded jitter and catch up after power-on. No unsupported timing guarantees.

Record last attempt, last successful snapshot and fixed actionable error categories in a private local status file. Preserve last success after a failed attempt. Status distinguishes schedule state, repository reachability, snapshot age/overdue and restore evidence. Remote status never changes the repository. A pending restore blocks scheduled capture. No retention deletion is performed; storage-capacity planning remains explicit.

Tests: failure-first status-age and preserved-success tests; root-runtime bundle validation with private temporary directories; actual systemd scheduled-run entry point against the disposable real SFTP repository; failed destination must preserve last success and return failure; timer-disable must preserve running backup. Existing backup/recovery and local suites remain required. Actual multi-location scheduling and alert delivery remain external acceptance.
