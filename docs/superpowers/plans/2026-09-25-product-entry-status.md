# Guided entry and operational evidence implementation

Follow the approved product goal and product-entry-status design. Execute inline, without subagents or additional milestone approval pauses. This checkout is separate from regional acceptance work. Never start clients, containers or servers on the developer computer.

## 1. Purpose and machine plan

- Test a strict journey schema for personal/institution/regional purposes, service choices, responsible operator, primary/recovery locations and new/existing network choices. Reject unknown fields and same declared location labels; explain that different labels are not proof of independent failure domains.
- Implement deterministic machine-role cards and ordered prerequisites. Regional application nodes stay on the institution's internal network; only the dedicated gateway joins the regional network. Personal service recovery is backup plus replacement capacity, not writable replication.
- Add private save/draft/resume through existing bundle writing. No saved file is executable and no role is marked installed from intent alone. Test cancellation, invalid resumes and preservation of existing bundles.

## 2. Guided actions using existing operations

- Add `rdc start` and `rdc guide JOURNEY`. Preserve the old `setup` command and menu numbers; append clear start/status choices.
- Implement a fixed menu of tasks for operator workstation, local node, chat, files, gateway, backup and recovery. Return allowlisted argument vectors to the existing parser/dispatcher, never shell strings or commands loaded from the record.
- Reuse role-specific wizards to collect domains, TLS and private inputs. Offer check/apply/account/enrollment/renewal/backup actions as explicit selections. Explain which machine each action affects before dispatch. Test routing, unsupported actions, cancelled selection and path quoting through argument lists.
- Generate a readable role checklist and write a concise beginner guide covering both new independent and existing/regional network paths.

## 3. Restore evidence

- Add tests for an owned, private completed restore result, failed/interrupted attempts and pending state precedence. Implement a record written only after a successful committed and finished restore, with captured/completed times and component identity.
- Keep service verification separate from user-operation proof. Do not invent a test date or translate a journal mtime into validated recovery evidence.
- Extend actual disposable recovery helpers to check the record and failure semantics.

## 4. Read-only summary

- Build bounded status collectors around existing owned-role checks. Report network, application, certificate, backup, recovery and partner dimensions independently with next actions.
- Use strict allowlisted output and classify permission/command/timeouts as unknown, not success. Test missing files, malformed/mixed roles, stopped services, stale backups, failed renewal and pending restore/partner states with file/probe fixtures.
- Add `rdc status` and a human-readable table plus optional JSON. It never requests sudo, starts services, refreshes runtime or writes a status cache.
- Add native status assertions to the existing Ubuntu acceptance fixtures without replacing real service/user tests.

## 5. Verify and integrate

- Run the focused tests, then the complete local/syntax checks once changes stabilize. Run relevant actual Ubuntu workflows, inspect results and fix observed failures.
- Review the complete diff, update evidence and current GitHub start instructions, and integrate only after the regional base and this increment pass. Keep human colleague acceptance and real physical/provider checks explicitly pending.
