# Nextcloud regional connector — implementation sub-design

Status: research and implementation contract; not an advertised working capability.

Extend the approved regional gateway design to the pinned Nextcloud 35.0.1 package. Each file VM keeps its one internal network membership. Its dedicated LAN connects only to its institution's regional gateway; that gateway has one regional membership. The already installed database, instance ID, user accounts, storage and internal HTTPS identity remain unchanged.

## Application transport

Generate a separate, root-owned configuration overlay and private LAN HTTPS listener. Do not add arbitrary PHP, proxy targets or proxy fragments from an imported document. Validate the same signed institution identity, independent fingerprint confirmation, exact local domain, gateway/service LAN addresses and current bilateral agreements used for Matrix.

All outbound Nextcloud HTTP uses the fixed LAN forward proxy, with no proxy exceptions. Keep TLS verification enabled. The gateway maps exact approved partner HTTPS names to signed regional addresses and rejects every other CONNECT destination, HTTP fallback and arbitrary port. Determine private-address validation from pinned upstream behavior; do not globally disable local-address protection to bypass an unexplained error.

Disposable run 36148407760 established that Nextcloud's DNS-pinning middleware rejects discovery before CONNECT when the private partner has no public DNS record. Its pinned implementation also explicitly rejects 100.64.0.0/10. While this fixed connector is active, set `dns_pinning=false`: the gateway's signed static address mapping replaces DNS resolution/pinning. Keep `allow_local_remote_servers=false`, TLS verification and an empty proxy exception list. The proxy must deny unknown names, IP literals, HTTP fallback and arbitrary ports; its mappings must never use DNS. A suspended connector restores the DNS-pinning default and directs HTTP to the closed local proxy endpoint. This is specific to the managed exact-destination connector, not advice for unrestricted Nextcloud proxies.

Start with explicit user-to-user file sharing. Enable only incoming and outgoing server-to-server shares; keep group federation, automatic acceptance, public links, global lookup upload, mail sharing and application-store access disabled. A recipient must explicitly accept a share. The application share token and permissions authorize file access independently of gateway membership. Require signed OCM requests where both pinned peers support them; verify successful and invalid/unsigned flows before advertising that protection.

## Candidate route catalogue to verify

This is a bounded source-derived candidate list, not permission to expose an entire app:

- Discovery: GET `/.well-known/ocm`, `/ocm-provider/` and, only if actually required, `/ocs-provider/`.
- OCM: POST the exact `/ocm/shares` and `/ocm/notifications` endpoints, including the product's actual front-controller prefix when generated by Nextcloud.
- Signing keys: GET `/index.php/apps/cloud_federation_api/api/v1/jwks`.
- Token exchange: POST `/index.php/apps/cloud_federation_api/api/v1/access-token`.
- Share data: `/public.php/webdav` and its descendants with the methods required for the tested share permissions. This route still requires the application's share credential. General user `/remote.php/dav`, browser login, account provisioning, administration and unrestricted OCS routes remain denied.
- Legacy `/ocs/v2.php/cloud/shares` notifications are not opened unless observed as necessary with the pinned pair and covered by separate tests.

Render the same route catalogue at both gateway ingress and the service LAN listener. Exact sources, hosts and upstream TLS identities remain mandatory. Application-generated discovery URLs must remain stable and use HTTPS. Test escaped paths, client/admin paths, unknown hosts and expired/absent approvals.

## Lifecycle

Hold the existing backup-first application operation lock during connector changes. Freeze matching reviewed runtime code; do not overwrite an older installed runtime implicitly. A durable pending marker disables the regional listener on interruption. Keep original internal config intact so failed attachment can restart internal files.

Keep connector approval state outside the application backup. Every restore writes a persistent suspension marker; recovered data must not reopen old regional access. Disable incoming/outgoing federation settings before a restored instance becomes writable, then require current approval review before re-enabling them. Backup validation still checks the original fixed application identity/configuration. Application background jobs must use the same selected configuration and proxy policy as the web process.

## Required disposable acceptance

Use two independent internal Headscale networks plus the regional network and actual pinned Nextcloud/PostgreSQL/Caddy/Envoy containers. Internal users upload distinct files over their own networks; create, explicitly accept and read an approved cross-institution share. Verify source/recipient identity, unrelated-file denial, unsigned/invalid OCM rejection when enforcement is enabled, unapproved destinations, general DAV/admin denial and no public links. Revoke the share and separately revoke the partnership, checking subsequent reads fail while acknowledging any already downloaded copy remains with its recipient.

Remove regional controller/gateways and prove both institutions can still log in, upload and read their own files. Run the existing encrypted backup/replacement restore workflow with the connector installed; prove restored files remain usable internally and partner transport stays suspended. These simulated networks do not establish home-NAT, physical-site or beginner acceptance.
