# Appliance V1 release inputs

The [release lock](../../appliance/releases/v1.lock.json) records reviewed official inputs as of 11 October 2026. It is an **unqualified base candidate**, not a bootable appliance release. The working machine is an ARM Mac without an x86-64 KVM runner or the target two-port hardware. Input provenance, unit checks and source inspection cannot establish installation or network safety.

`release_id` is `appliance-v1-base-20261011`; `adapter_id` is `pve-9-2-1`. Each byte limit equals the exact expected file size, so extra bytes fail verification. A downloaded input must match both size and digest before use. Compressed and expanded identities are distinct. The output bundle requires its own manifest; none of these hashes identifies an assembled appliance ISO.

## Probe and Linux role base

`probe-image` and `linux-base` intentionally refer to the same immutable vendor bytes. They are separate capability records and must create separate VM disks and local seeds. A build may deduplicate immutable storage by digest, but must never reuse a running VM or enrollment state across roles.

The [Ubuntu package manifest](https://cloud-images.ubuntu.com/releases/noble/release-20260926/ubuntu-24.04-server-cloudimg-amd64.manifest) lists `bind9-dnsutils`, `bind9-host`, `curl`, `iproute2`, `netcat-openbsd`, `openssl`, `python3`, `systemd-timesyncd` and `tcpdump`. This supports choosing it as the neutral probe input; it does **not** prove these tools work in the assembled appliance. Before acceptance, generate a local NoCloud seed with console access, stable NIC mapping and site-specific networking; disable package upgrades, package downloads and automatic enrollment. Console credentials must be unique per local instance and never embedded in the reusable image.

Qualify offline console login, actual virtual disk geometry, DNS queries, explicit NTP service checks, HTTPS validation and known listening endpoints. Time synchronization alone does not prove that an NTP server is reachable or correct. The probe must start without role provisioning or an Internet download. Its disposable disk must contain no persistent client/controller/relay identity. These seed and runtime checks are outstanding.

The `tailscale`, `headscale` and `derper` role binaries and their complete offline provisioning inputs remain explicitly missing. Role builds must refuse those capabilities until actual reviewed inputs are added. Their absence does not justify fabricating hashes, silently installing the latest package, or calling the base candidate complete V1.

This is a pinned source candidate for the assistant and adapter review. The official Trixie package index lists `proxmox-auto-install-assistant_9.2.5_amd64.deb`, 1,072,052 bytes, SHA256 `9a61e37c3efce192a5ea86af06b3ccf7027fe581226068911d4833f4af7ac83e`. This package is **not** a trusted executable input in the lock: the observed download host's HTTPS certificate did not validate, and the alternative HTTP APT metadata was not authenticated locally. On the Linux build runner, use the official [Proxmox package repository](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#sysadmin_package_repositories) with successfully authenticated APT metadata and verify that exact package identity, or reproducibly build the assistant from the pinned source with its own complete toolchain/dependency lock. Neither route is complete here. Do not fall back to unauthenticated HTTP or disable certificate verification.

A read-only ISO9660 directory range inspection of the official ISO found product metadata `RELEASE='9.2'`, `ISORELEASE='1'`, `PRODUCT='pve'`, a 113,561,600-byte base SquashFS entry and a 644,259,840-byte installer SquashFS entry. The range inspection used short ISO9660 names, not a complete Rock Ridge extraction. It does not establish exact live filesystem paths, the packaged installer version, or integrity of the whole ISO. The full pinned ISO must be verified and extracted before an adapter accepts any path or replacement hash.

Upstream [automated installation](https://pve.proxmox.com/wiki/Automated_Installation) provides answer validation, device inspection/matching and `prepare-iso`. It does not provide the appliance's interactive hardware gate, trusted storage ancestry decision, offline large-payload staging, or repair ownership rules. Its live [launcher](https://github.com/proxmox/pve-installer/blob/32afcd4cd534d8e2f99ae76aa0234a0a5c697ba9/unconfigured.sh) starts networking before the automated front end. Merely preparing an answer with a static address does not satisfy the no-host-WAN-address requirement.

The release-specific integration must therefore establish all of the following on the exact verified ISO:

1. Extract the boot records, kernel/initrd and live filesystem; identify packaged installer/assistant versions and hash every upstream file that will be replaced. Reject unknown layouts or hashes. Preserve the boot structure when rebuilding and inspect the rebuilt image again.
2. Replace the earliest live dispatch path with the appliance menu **before** DHCP, SLAAC, time synchronization or upstream installation. Disable IPv6 at kernel startup and keep physical links down until the local gate assigns roles. Cover every boot-menu path; leaving an automatic fallback to stock installation defeats the gate.
3. Keep answer generation in private RAM, after fresh inventory, exclusion of all USB backing storage, NIC identification and typed disk/plan confirmation. Reject shared or spanning storage and non-target conflicting `pve` volume groups: upstream collision handling can otherwise rename existing storage. There is no permission to erase from a cached plan alone.
4. Validate the generated answer using the qualified assistant. Invoke the pinned automated front end and its official low-level installer, with reboot held. Prove the exact stdin/environment/task-completion contract; do not implement a replacement partitioner.
5. After confirmed installation, identify the new root filesystem as belonging to the selected target. Use the release's supported mount helper only after that check. Copy the appliance payload, per-site plan, verified OPNsense ISO and probe input to internal storage; fsync the completion marker last. Failed or interrupted staging must not announce a usable host or trigger another erase.
6. Install the small `before-network` first-boot executable and recovery units. The upstream [first-boot service](https://github.com/proxmox/pve-installer/blob/32afcd4cd534d8e2f99ae76aa0234a0a5c697ba9/proxmox-first-boot/etc/proxmox-first-boot-network-pre.service) runs on the **installed system, after disk erasure**. The executable size limit is 1 MiB; it cannot transport the router ISO. Stage early safe host files before networking, then apply and verify PVE/pmxcfs-dependent firewall configuration later before guest/WAN activation.
7. Keep all OPNsense vNICs disconnected during its live DVD and first disk boot. Its defaults must not expose DHCP/RA on management. Qualify console configuration, persistent disk-only boot and restricted administration before linking management or WAN. The live DVD is not evidence of an installed router.
8. Give USB Repair its own read-only discovery and explicit existing-host selection. Repair never reaches the installer/partitioner path. A USB left inserted must always return to a safe menu without replaying an answer.

These are required integration checks, not claims that a custom ISO already implements them. Stock `prepare-iso` plus a first-boot script alone is insufficient.

## Qualification and redistribution gates

Use the initial disposable lab allocation of 4 vCPU, 16 GiB RAM and a 128 GiB disk. The lock's individual host/VM budgets are provisional starting allocations, not published minimum requirements. Account for downloaded and expanded media, temporary installer space, guest disks and measured peak use before qualifying any budget. The profile and budgets remain `unqualified`; an explicit disposable qualification build may use them, but a release publisher must refuse them.

The narrow M0 gate requires a verified complete Proxmox ISO; a qualified exact assistant/source match; actual ISO extraction/rebuild tools; and a disposable x86-64 Linux KVM runner with UEFI, independent target/canary disks, management peer and DHCP/RA WAN peer. Capture startup traffic to prove no host WAN address is acquired. Hash every disk before/after cancellations and refusal cases, including non-target conflicting storage. Prove that successful staging survives USB removal and that leaving USB inserted cannot reinstall. Run interrupted-staging and no-upstream boots. Missing tools, hardware or evidence must report **NOT RUN**, never PASS. Physical two-port testing remains a separate gate after the disposable lab succeeds.

Before redistribution, collect the exact shipped copyright/license notices and corresponding-source obligations for the full Proxmox, OPNsense and Ubuntu distributions; each contains software under multiple licenses. Preserve the upstream Restic source and license notice at its pinned release. The current `source` links identify upstream projects; they are not a complete source archive or a completed redistribution inventory. No public release or complete V1 claim is authorized by this input record.
